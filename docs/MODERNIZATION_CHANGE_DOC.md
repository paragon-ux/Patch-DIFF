# PatchDIFF Product Change Record

PatchDIFF provides four declarative transaction formats through one deterministic applier and locked PostgreSQL submission pipeline. Authoritative reads, advisory preview, durable outcome recovery and deterministic replay let hosts propose and verify changes without moving state authority into the host.

Architecture and contracts: [architecture](MODERNIZATION_ARCHITECTURE.md), [MCP tools](MCP_TOOLS.md), [core runtime](PATCHDIFF_CORE_SPEC.md), [storage](DATA_MODEL.md), [transaction formats](PDCP_FORMAT.md), [host guide](HOST_INTEGRATION_GUIDE.md), and [legacy compatibility](LEGACY_COMPATIBILITY.md).

## Transaction formats and compatibility

| Tool | Stored protocol | Runtime for new submissions | Behavior |
| --- | --- | --- | --- |
| `patchdiff_submit_edits` | `patchdiff-tx/1` | `patchdiff-mvp-0.2.2` | Typed exact matches with intent and required version/hash guard. |
| `patchdiff_submit_operations` | `patchdiff-tx/2` | `patchdiff-mvp-0.3.0`; `patchdiff-mvp-0.5.0` when a span carries `expected_before`/`expected_after` | Ordered exact match/span operations; spans require exact expected text, can check the exact adjacent text, and use sequential code-point coordinates. Empty-span insertion is explicit. |
| `patchdiff_submit_replacement` | `patchdiff-tx/3` | `patchdiff-mvp-0.4.0` | Exactly one guarded `replace_all`; empty replacement is valid. One typed ledger fact covers the full original span. |
| `patchdiff_submit_pdcp` | `0.2.3` | `patchdiff-mvp-0.2.2` | Frozen legacy text format; see [LEGACY_COMPATIBILITY.md](LEGACY_COMPATIBILITY.md). |

Fresh replacement raw text and canonical result each have inclusive limits of 1,000,000 code points and 1,048,576 UTF-8 bytes. Invalid Unicode follows the audited encoding-rejection path. Existing-key recovery/conflict precedes fresh admission. Oversized valid fresh replacements return `invalid_argument/replacement_too_large` without writes; replay does not reapply fresh admission limits. Runtime 0.3.0 continues to reject `replace_all`.

Profiles are immutable. Replay dispatches on the stored protocol/runtime pair, preserving 0.1.0 non-overlapping matching, 0.2.0 historical typed change-ID grammar, 0.2.1 strict typed IDs, and the pre-0.2.2 ignored-singleton-selector behavior. Current match-capable profiles enforce every supplied selector, even for one occurrence. Runtime 0.5.0 adds only span context guards; tx/2 records without them keep 0.3.0. Unknown protocol/profile pairs fail closed; historical records and fingerprints are not rewritten.

## Atomicity, identity and audit

Each accepted transaction applies all changes sequentially in memory and commits atomically per target under `SELECT ... FOR UPDATE`. The append-only attempt log records admitted accepted and rejected submissions; the accepted-only ledger carries `origin` and runtime-derived spans, character counts and hashes. `ValidationStage` determines validity; task correctness and semantics remain `not_evaluated`.

Exact keyed recovery returns the original outcome before stale guards and appends no row. Conflicting reuse creates a distinct rejected NULL-key row with the submitted fingerprint, original-log linkage and bounded key preview. The original keyed row stays immutable. Request identity includes the full canonical raw proposal and guards; sorted JSON keys do not normalize decoded strings, omitted/null edit fields, advisory prose or selectors. Eligible same-target rejected parent UUIDs canonicalize; ineligible parent spellings retain their existing rejection identity.

Unpaired surrogates and NUL are rejected without repair. Known-target invalid input is preserved reversibly as ASCII-escaped `patchdiff-invalid-input/1` evidence in existing TEXT fields, with safe JSONB diagnostics. Valid serialization, hashes and historical recovery identities stay unchanged. Read/search text argument errors create no edit-attempt row. Stdio explicitly uses strict UTF-8 input/output, including on Windows; malformed wire bytes are not repaired.

Locked submission and replay reads refresh canonical state. PostgreSQL READ COMMITTED supports lock-then-read recovery; callers selecting stronger isolation own serialization/deadlock retries. Caller-owned transactions retain commit/rollback and lock-lifetime ownership; infrastructure errors are not masked as validation rejections.

## Bounded reads, diagnostics and preview

Offset reads default to 4,000 and cap at 8,000 code points. Line reads use one coherent ordinary column observation under `no_autoflush`, inclusive one-based LF-only ranges, trailing-newline inclusion and the final empty line. Continuation is relative to the selected range (`next_offset`) or absolute (`next_start`), and opt-in `line_starts` give absolute line offsets; no local state is flushed. Exact search counts overlapping occurrences and caps context at 400 code points. History defaults to 50 rows, caps at 200 and uses exclusive sequence cursors; attempts descend, while each selected newest ledger page displays ascending.

Rejections preserve immutable original `diagnostic.failure_context` and expose separate fresh response-only `current_context`. A known failure location beyond the start of the text makes `failure_context` a window around it; an MCP `current_context` identical to it is returned as unavailable (`same_as_failure_context`). Each has at most 256 code points and 4,096 compact ASCII-escaped JSON bytes; together they fit 8,192 bytes including wrappers. Canonical/intermediate buffer labels and prior-change counts do not imply a partial commit. Older diagnostics are never retrofitted. Optional correlation is a fresh invocation UUID, including recovery, and never changes durable identity.

Exact diagnostic candidates are limited to five, with 20-code-point side contexts, a 64-code-point match preview and an 8,192-byte wrapper. Immutable failed-query evidence is capped at 64 code points and 1,024 wrapped bytes. Near misses are response-only after successful service-owned commit/lock release, explicitly omitted for caller-owned transactions and for consumed sequential matches. Fresh rejections scan a never-persisted copy of up to 65,536 code points of the failing buffer; exact recovery scans the stored context. Distances use an exact Ukkonen-banded Landau–Vishkin Levenshtein program (`band_radius = (threshold + 1) // 2`) with exact positional pigeonhole filtering within a 1,000,000-cell cap; reaching the cap stops at a window-start boundary and reports the scanned range. Windows are query length ±1, the threshold is `min(4,max(1,length//4))`, and up to three non-overlapping candidates are ranked by distance/start/end, with 16-code-point side contexts and an 8,192-byte wrapper. Combined new enrichment is capped at 18,432 compact ASCII-escaped JSON bytes, excluding preexisting arbitrary evidence. Suggestions never select or apply a fuzzy edit. Span failures report `span_check`, `buffer_length` and up to 64 code points of `actual_text`; `sequential_match_invalid` names the earlier change that consumed each original occurrence. `diagnostic.retryable` follows one shared definition.

Accepted responses carry `current_version`/`current_hash` next to `version`/`after_hash`, plus advisory warnings (`no_op_change`, `no_op_transaction`, `occurrence_index_basis_shift`, `grapheme_boundary_split`) that are stored on accepted rows only when present and returned on exact recovery. Request-key conflicts carry `diagnostic.code: "request_key_conflict"` with the differing fingerprint components and record fields. Tool-result text is literal inside ASCII-escaped JSON-RPC lines, and unknown or missing tool arguments return a structured `invalid_argument` payload.

Preview uses the shared fresh guard/decode/apply evaluator, one coherent observation and an explicit format. It has no request key, lineage, audit, writes, locks, commit or rollback; pending local target changes are rejected without flushing. Rejected previews return no partial facts. Submission always re-locks and rechecks; a preview reserves no state.

The complete preview payload is capped at 32,768 compact ASCII-escaped JSON bytes, excluding transport envelopes. Accepted facts form a prefix of at most 32 complete facts, 2,048 bytes each and 16,384 bytes including the wrapper. Text evidence caps at 1,024 code points/8,192 wrapped bytes per field; diagnostic wrappers cap at 16,384 bytes. Explicit counts and omission metadata retain verdict, reached stage, valid target/observed identity and accepted hash. Oversized identities are omitted, never shortened. [MCP_TOOLS.md](MCP_TOOLS.md) defines deterministic omission order. Ordinary submission/recovery facts and stored audit evidence remain complete.

Discovery examples are deep-copied per result and bounded: 65,536 compact ASCII-escaped JSON bytes for discovery, 8,192 bytes for the complete examples map. The host guide gives the executable sequence binding returned IDs, guards, parents and cursors, including deduplication and complete history traversal.

## SAVE, replay and schema

SAVE snapshots current target state and rotates editing cycles without mutating content; optional version and hash guards are both checked. Replay checks initial snapshot ownership/hash, accepted-log ownership/content hashes, contiguous versions, before/after hashes and recorded execution profiles. Materialized health reports independent raw `content_matches`, `stored_hash_matches`, `recomputed_hash_matches` and `version_matches`; successful reconstruction can coexist with unhealthy storage. CRLF/bare-CR corruption is visible even if canonical hashes agree. Replay never repairs target or history.

Migrations are `20260510_0001`, `20261020_0002` and `20261022_0003`. Migration 0002 adds ledger origin/derived facts, request key/fingerprint and the target/key partial unique index; typed ledger prose may be null. Downgrade refuses existing typed ledger rows rather than discarding information. Migration 0003 adds nullable `cloud_target_files.source_line_endings`, recorded for new uploads before LF canonicalization; existing targets keep NULL, and downgrade refuses while recorded facts exist. `patchdiff_export_target` honours `original_text` (canonical LF, the default), `canonical_lf`, `crlf` and `original_eol` and refuses other formats. Ledger and attempt pages expose their join keys, bounded intent and a per-page content byte budget without schema changes.

## Verification scope

[TEST_MATRIX.md](TEST_MATRIX.md) maps unit, live PostgreSQL, populated migration preservation/refusal and real stdio workflows (`1,226` automated tests: `816` unit + `410` live PostgreSQL/stdio integration, plus `235/235` live stdio friction checks at `PR #14`). [Evaluation documentation](../evaluation/README.md) records deterministic byte accounting (`151 B` wire for 1 minimal `tx/1` edit, `259 B` for 5 edits, `341 B` `tools/call` line for small `tx/3` replacement), `SVC-001` 65,536-code-point near-miss latency (`1.7 ms` on varied prose, `41.9 ms` with 100% scan coverage on repetitive logs), and `MCP-001` PostgreSQL 16+ `LATERAL` history/ledger latency over 20 MB substrates (`14.68 ms` ledger / `22.85 ms` log on `50 × 400 KB` `tx/3`; `136.72 ms` log / `221.59 ms` ledger on `20 × 1 MB` `tx/1`). Test counts and CI results apply only to their executed revision; this record does not certify current publication CI.

Offline replacement cases measure serialized bytes and accepted content/hash oracles, not live transport, persistence or timing. No live-model comparison, representative sanitized dataset or production performance threshold has been established. No editing adapter, optional typed guards or normalized request-identity behavior is introduced.

Historical source and verification records remain preserved in Git and internal archives; they do not establish verification of a later revision.
