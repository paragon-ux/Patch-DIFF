# Goal F Pass A decisions: correlation, bounded diagnostics, guarded operations

Status: accepted implementation choices under the user's consolidated execution authority in EXECUTION-PLAN.md. F01 foundation is 128f59d; F02 optional guards and F04 normalized identity remain deferred. No migration or old-profile reinterpretation.

## F03 response correlation

All three public submission tools accept `include_correlation_id: boolean = false`. True returns a fresh UUIDv4 `correlation_id` for that invocation, including rejected and exact-deduplicated outcomes. False/omitted adds no correlation field. It is response metadata, never a retry key, persisted lookup, fingerprint field or log rewrite. Caller-supplied `client_request_id` remains the sole keyed-recovery identifier. Invalid non-boolean values return `status: invalid_argument` before submission admission and create no attempt; this response-option boundary is distinct from audited transaction-domain rejections. The service API enforces the same boundary. UUIDv4 uniqueness is probabilistic; correlation does not recover a lost response.

## F06 bounded exact rejection candidates

For applicability `match_ambiguous` and `disambiguation_invalid`, capture at most the first five exact occurrences in left-to-right order from the actual failing buffer. Each candidate contains one-based `occurrence_index`, end-exclusive code-point `start/end`, at most 20 code points of `before/after`, and at most 64 code points of `match_preview` plus `match_truncated`. The existing complete occurrence count is retained; inspect at most five spans for diagnostic text, with no extra full-document diagnostic scan beyond the existing applicability enumeration/count. Persist `diagnostic.exact_candidates` once, including kind, count, returned count, truncation and the F01 buffer stage/prior count/transaction-start observed identity. Cap the entire `{exact_candidates: ...}` compact ASCII-escaped JSON wrapper at8192 bytes by dropping trailing candidates if needed; do not truncate identity. No continuation cursor or automatic selection. Exact-key recovery returns original evidence unchanged. Outer `failed_change_id` identifies the failed operation. Intermediate indices refer to simulated text and cannot be paged against committed target text.

## F05 near misses after actual lock release

For applicability `match_absent` and `sequential_match_invalid`, persist only bounded immutable query evidence alongside F01 failure context: `diagnostic.near_miss_query`, containing canonical query text when its raw length is at most 64 code points, otherwise explicit `match_too_large`. Its complete wrapper is at most1024 compact ASCII-escaped JSON bytes. Never capture another full failure buffer.

After `_submit` returns from a successfully committed service-owned transaction, compute response-only top-level `near_misses` exclusively from the stored original failure prefix (at most 256 code points) and bounded query. No reread of a newer target, lock reacquisition, persistence retry, additional attempt, background job or diagnostic rewrite. Caller-owned transactions skip computation and return `caller_transaction` omission without committing/releasing their locks. Exact recovery uses the original persisted query/context and follows the current call's ownership boundary. Historical outcomes lacking these inputs return `historical_context_unavailable` rather than retrofitting evidence.

Search fixed windows of query length-1, length and length+1 (positive lengths only) entirely inside the captured prefix. Compute ordinary code-point Levenshtein distance; compare at most 1,000,000 DP cells total. On exhaustion return `work_budget_exhausted` with no partial candidates. Accept nonzero distances at most min(4,max(1,len(query)//4)). Sort by `(distance,start,end)` and return at most three candidates, with up to 16 before/after code points. Text is at most 65 code points per candidate. Empty or no-near prefix returns an explicit computed empty list. Results say `kind: near_miss`, never exact match or applicable edit. Truncation reflects prefix omission or candidate-count truncation; no cursor or promise of distant matches. Include original buffer stage/prior count/observed identity, never current identity relabeled as original. Entire `{near_misses: ...}` wrapper is at most8192 compact ASCII-escaped JSON bytes; drop trailing candidates if needed with truncation. Bounded query, work exhaustion and historical/caller omissions are expected structured states. Unexpected exceptions propagate after commit and do not imply rollback of the recorded verdict.

F01 pair stays at8192 bytes. Exact and near candidate enrichments are mutually exclusive per failure. Together with the query and optional UUID, all newly added enrichment fields fit18432 compact ASCII-escaped JSON bytes; this does not claim to bound preexisting arbitrary diagnostic/request evidence or the entire response.

## F07 explicit guarded sequential operations

Add `patchdiff_submit_operations` with durable `format: patchdiff-tx/2` and ordered `operations`. Required top-level intent and at least one hash/version guard retain existing validation/audit/lineage/idempotency behavior. Each operation is explicit `op: match` or `op: span`, with optional existing `change_id/rationale/risk`. Match operations have the existing match/replace/selectors semantics. Span operations require non-boolean integer `start/end` in 0..2^63-1, end>=start, exact `expected_text` and string `replace`; selectors, `match`, unknown fields and unknown operations reject. Use sequential canonical-buffer code-point coordinates, end exclusive. Canonicalize expected/replacement newlines as existing payloads do; compare canonical expected text exactly against the specified span. Bounds beyond the current buffer reject `span_out_of_bounds`; expected text disagreement rejects `span_expected_text_mismatch`, both at TRANSACTION_APPLICABILITY. Structural span errors reject at PROTOCOL_VALIDATION. Mixed match/span edits are allowed in declared order and atomic. Zero-length insertion is allowed only when the selected empty span equals empty canonical expected text; legacy/v1 empty MATCH stays invalid. Deletion uses an empty replacement.

Lower both operation types into the shared ParsedPDCP/applier; extend PDCPChange with explicit operation/start/end fields defaulting to historical match behavior. Record a distinct immutable `patchdiff-mvp-0.3.0` profile enabling spans, overlapping exact matches and singleton-selector enforcement. Existing typed/legacy submission tools keep recording 0.2.2 and keep their exact original record/fingerprint forms. New operation records use existing canonical JSON and fingerprint machinery with their explicit format/operation fields; no historical rewrite or normalized identity. Existing typed ledger origin remains `typed`, with usual derived spans/counts/hashes; span facts also identify `operation: span`. New accepted/rejected attempts use the same lock/rejection/ledger pipeline. Caller ownership and qualified audit remain unchanged.

Replay dispatches tx/2 only with a profile explicitly supporting spans; old, missing and unknown profiles fail closed for these new operations. New 0.3.0 never includes future replace_all semantics; F09 is Pass B and needs its own profile. Discovery exposes the new input schema and x-patchdiff-capabilities describing tx/2, profile, operation names, sequential code-point coordinates and insertion policy. F12 executable examples remain Pass B.
